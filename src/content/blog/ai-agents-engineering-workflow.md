## 1. 탭(Tab) 자동완성에서 '에이전트(Agent)'의 시대로

처음 GitHub Copilot이 나왔을 때만 해도 "인라인 자동완성이 참 편하다" 정도의 인상이었습니다. 하지만 지금의 AI 코딩 에이전트(Claude 3.7 Sonnet, Cursor Agent, Antigravity 등)는 질적으로 완전히 다릅니다.

지금의 에이전트는 코드베이스 전체를 검색하고, 파일 간의 참조 관계를 파악하며, 터미널 명령어를 직접 실행하고, 빌드 에러를 스스로 읽고 수정하는 **'주니어 이상급의 페어 프로그래머'** 역할을 수행합니다.

그렇다면 프로덕트 엔지니어는 이 강력한 도구를 어떻게 실무에 녹여내야 할까요?

---

## 2. 실무 효율을 3배 높여준 3단계 에이전트 워크플로우

### Step 1. 컨텍스트 주입 (Context Feeding)
AI 에이전트가 엉뚱한 환각(Hallucination)을 일으키거나 프로젝트 컨벤션을 무시하는 가장 큰 이유는 **'맥락 부족'** 때문입니다.

- **`AGENTS.md` / `.cursorrules` 활용:**  
  프로젝트 루트에 기술 스택, 디렉토리 구조 규칙, 테스트 방법, 런타임 제약사항을 명확히 명시합니다.
- **도메인 모델 먼저 정의하기:**  
  비즈니스 로직을 짜게 하기 전, 핵심 인터페이스(Types)나 스키마(Schema)를 먼저 확정하여 에이전트에게 가이드라인으로 제공합니다.

### Step 2. '설계 검증' 먼저, '코드 작성'은 나중에
많은 개발자가 범하는 실수는 에이전트에게 곧바로 *"이 기능을 만들어줘"*라고 요청하는 것입니다. 이 경우 나중에 고치기 힘든 거대한 스파게티 코드가 나오기 십상입니다.

제가 정착시킨 패턴은 다음과 같습니다:
1. **문제 정의 및 요구사항 전달**
2. **에이전트에게 2~3가지 아키텍처 대안과 트레이드오프 요청**
3. **엔지니어가 최적의 설계를 선택하고 스텝별 구현 계획(Plan) 수립 지시**
4. **승인된 계획에 따라 파일 단위로 점진적 구현 진행**

이 과정을 거치면 코드 퀄리티는 사람이 짠 것 이상으로 탄탄해지며, 버그 발생률이 급감합니다.

### Step 3. 테스트 주도 검증 (TDD with Agent)
에이전트의 진정한 힘은 **'자기 수정 루프(Self-Correction Loop)'**에서 나옵니다.
- 단위 테스트(Unit Test)를 먼저 작성하게 하거나,
- 코드를 작성한 뒤 터미널에서 `npm test` 또는 `swift test`를 실행하게 하여,
- 실패한 테스트 출력을 직접 보고 스스로 코드를 고치게(Self-healing) 만듭니다.

## 3. '바이브 코딩(Vibe Coding)'의 함정과 엔지니어의 역할

요즘 유행하는 *'바이브 코딩(코드를 전혀 보지 않고 느낌으로만 AI에게 시켜서 만드는 개발)'*은 빠른 토이 프로젝트나 프로토타입 검증에는 환상적입니다.

하지만 프로덕션 레벨의 서비스에서는 반드시 위험이 따릅니다:
- 보안 취약점 (SQL Injection, 취약한 인증 토큰 처리)
- 엣지 케이스 처리 누락 및 예외 전파 구조 붕괴
- 장애 발생 시 원인 추적 불가능

결국 **"최종 책임은 엔지니어에게 있다"**는 원칙을 잊지 않아야 합니다. AI가 생성한 코드의 동작 원리를 정확히 이해하고, 코드 리뷰를 꼼꼼히 수행하며, 시스템의 아키텍처적 일관성을 지키는 것이 AI 시대 엔지니어의 핵심 덕목입니다.

---

## 4. 요약: 엔지니어는 오케스트라의 지휘자가 된다

과거의 개발자가 벽돌을 하나하나 쌓는 '석공'이었다면, 지금의 프로덕트 엔지니어는 여러 AI 에이전트와 도구를 조율하는 **'오케스트라 지휘자'**에 가깝습니다.

AI를 두려워할 필요도, 맹신할 필요도 없습니다. 가장 뛰어난 조력자로 길들이는 사람이 결국 시장에서 가장 앞서나갈 것입니다.
