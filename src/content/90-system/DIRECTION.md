# 🧭 방향 헌장 (Direction Charter)

이 문서는 **사용자와 모든 AI 에이전트가 공유하는 기준선**입니다. 저장소에서 작업하는 에이전트는 세션 시작 시 이 문서를 읽고, 구조나 방향에 영향을 주는 작업을 하기 전에 "이 작업이 아래 목표 중 무엇을 위한 것인가"를 한 문장으로 말할 수 있어야 합니다. 말할 수 없으면 작업하지 않고 사용자에게 묻습니다.

방향이 바뀌면 이 문서를 고치는 것이 아니라 **맨 아래 결정 로그에 날짜와 함께 덧붙입니다.** 과거의 결정을 지우지 않습니다.

---

## 1. 목표 (순서가 있음)

1. **방향을 함께 정하고, 사람과 달리 지속 가능하고 일관성 있게 구성한다.**
   사람은 기분, 기억, 일정에 따라 기준이 흔들린다. 판단을 규칙 파일, 스킬, 템플릿으로 꺼내 놓아 에이전트가 매번 같은 기준으로 실행하게 한다.
2. **그 기준을 회사 전반의 작업에 일관되게 적용한다.**
   iOS, Android, React Native, 웹 어느 저장소에서 일하든 같은 PR 규칙, 같은 설계 기록 형식, 같은 리뷰 체크리스트가 따라다닌다.
3. **기획부터 개발 완료까지 혼자 End-to-End로 해내는 프로덕트 엔지니어(PE)가 된다.**
   PRD, 인수 조건, 기술 명세, 구현, QA, 릴리스까지. 문서도 코드와 같은 수준으로 에이전트가 생산하고 검증한다.

## 2. 세 기둥 (모든 작업은 최소 하나를 도와야 함)

- **제2의 뇌** — 원자 노트, 설계 기록, 용어집. 판단의 근거가 쌓이는 곳.
- **AX 도입** — 에이전트 규칙, 스킬, 기억의 통합 파이프라인. 판단이 실행되는 곳.
- **PE 및 개발 전환** — iOS 네이티브에서 RN, 분산 시스템, 기획 문서까지. 판단이 넓어지는 방향.

## 3. 원칙

- **절차가 중심, 지식은 그 뒤.** 매번 읽혀야 하는 것은 규칙과 절차다. 용어집과 위키는 **막힐 때만 보는 참조층**이며, 모든 에이전트 컨텍스트에 주입하지 않는다.
- **특정 패턴을 맹종하지 않는다.** Karpathy LLM Wiki, CoALA, A-MEM 등은 참고일 뿐이다. 더 좋은 방법이 있으면 언제든 채택한다.
- **암묵지는 사용자의 실제 경험만 적는다.** 에이전트가 사례를 지어내지 않는다. 모르면 묻는다.
- **검증되지 않은 도구는 도구가 아니다.** 규칙을 만들면 그것을 검사하는 린트나 테스트를 함께 만든다.
- **조용한 실패를 허용하지 않는다.** 충돌, 누락, 드리프트는 warning이 아니라 error로 드러나야 한다.
- **날짜와 사실은 추측하지 않는다.** `date +%F`, `git log`, 실제 파일을 확인한다.

## 4. 비목표 (하지 않는 것)

- 용어집 개수를 늘리는 것 자체. 🧭 실무 판단이 없는 용어는 백과사전 복제일 뿐이다.
- 모든 에이전트가 위키 전체를 읽게 만드는 것.
- 회사 내부 식별자, 에러 코드, 비공개 URL을 공개 위키에 적는 것. 원칙 수준으로 추상화한다.
- 사용자가 직접 타이핑해서 유지해야 하는 목차나 색인.

## 5. 층 구조

| 층 | 역할 | 위치 | 누가 읽나 |
|---|---|---|---|
| 방향 | 이 문서 | `90-system/DIRECTION.md` | 모든 에이전트, 세션 시작 시 |
| 절차 | 규칙(AGENTS.md), 스킬, 템플릿, 체크리스트 | 각 저장소 루트와 공용 스킬 패키지 | 모든 에이전트, 매 작업 |
| 지식 | 설계 기록, 용어집, 개념 노트 | `10-wiki/` | 막힐 때만 |
| 일화 | 트러블슈팅, 회의 메모, PR, inbox | 각 저장소, `00-inbox/`, `30-projects/` | 승격 작업 때 |

## 6. 드리프트 점검 (엇나감을 잡는 방법)

- **작업 전:** 구조나 방향에 영향을 주는 작업이면 "목표 1·2·3 중 무엇을 위한 것인가"를 한 문장으로 적는다. 없으면 멈추고 묻는다.
- **작업 후:** `npm run lint:glossary`의 🧭/sources 비율, `npm test`, `npm run build`가 통과해야 한다.
- **주기적:** 외부 평가자(Orca로 Claude·Antigravity 등)에게 브리프 없이 저장소만 주고 "이 프로젝트가 무엇을 하려는지, 되고 있는지"를 채점받는다. 점수는 `AGENTS.md`가 아니라 이 문서의 결정 로그에 남긴다.
- **기록 위치:** 사용자와 에이전트의 방향 합의는 에이전트의 사적 메모리가 아니라 **이 문서**에 남는다. 에이전트 메모리에는 이 문서를 가리키는 포인터와 세션 연속성에 필요한 사실만 두고, 방향 내용을 복사해 두지 않는다.
- **충돌 처리:** 이 문서와 에이전트 메모리, 또는 이 문서와 실제 작업 방향이 다르면 **어느 쪽도 자동으로 우선하지 않는다.** 에이전트는 작업을 멈추고 두 내용을 나란히 보여준 뒤 사용자와 함께 어느 쪽이 맞는지 정하고, 틀린 쪽 하나를 고친 다음에만 진행한다. 헷갈리는 이중 구조를 남겨두는 것이 가장 나쁜 결과다.

## 7. 다음 사이클

1. PRD, 인수 조건, 설계 기록 템플릿과 리뷰 체크리스트를 **스킬로 묶어** 어느 저장소에서든 같은 방식으로 호출되게 한다. 기존 spec-reviewer, QA 에이전트, commit-message 스킬을 하나의 체계로 모은다.
2. 공용 절차 패키지를 회사 저장소들(iOS, Android, RN)의 AGENTS.md에 연결한다.
3. 블라인드 재평가로 점수 이동을 확인한다.
