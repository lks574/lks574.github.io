## 1. 작업 시작 전 체크리스트

분석을 시작하기 전에 아래 형식으로 체크리스트를 먼저 출력합니다.
**작업 모드(`draft` 신규 작성 / `update` 부분 갱신)** 를 가장 먼저 식별합니다. 사용자가 "구현 결과를 spec 에 반영" 을 요청한 경우(`sync` 모드) 는 거부하고 PR description / 태스크 파일 / `decisions.md` 로 안내합니다.

항목은 프로젝트 성격에 맞게 3~7개로 조정합니다.

```markdown
## 📋 작업 체크리스트

- [ ] **작업 모드 식별** (draft 신규 작성 / update 부분 갱신)
- [ ] 명세 문서 및 Figma 전체 검토
- [ ] 기능 범위 및 경계 조건 식별
- [ ] 누락된 엣지 케이스 및 예외 처리 점검
- [ ] 데이터 모델 및 인터페이스 정의 완전성 확인
- [ ] 모호하거나 불분명한 요구사항 목록화
- [ ] 사용자에게 확인이 필요한 질문 정리
- [ ] 최종 Tech Spec 문서 작성 및 자기 검증
```

## 2. 기능 명세 점검 항목

### 2.1 기능 흐름
- [ ] 각 기능의 입력값 / 출력값 / 상태 변화가 명확히 정의되었는가?
- [ ] 정상 흐름(Happy Path)이 완전히 서술되었는가?
- [ ] 예외 흐름(Error Path / Edge Case)이 빠짐없이 정의되었는가?
- [ ] 전제 조건(Pre-conditions)과 사후 조건(Post-conditions)이 명시되었는가?

### 2.2 권한 및 보안
- [ ] 권한 및 접근 제어 조건이 명시되었는가?
- [ ] 인증(Authentication)과 인가(Authorization)가 구분되어 정의되었는가?
- [ ] 민감 데이터 처리 방침이 정의되었는가?

### 2.3 데이터 및 유효성
- [ ] 데이터 유효성 검증 규칙(길이, 형식, 범위 등)이 정의되었는가?
- [ ] 데이터 모델의 필드·타입·제약조건이 명시되었는가?
- [ ] 데이터 생명 주기(생성·수정·삭제·보관)가 정의되었는가?

### 2.4 비기능 요구사항
- [ ] 성능 목표(응답 시간, 처리량)가 수치로 정의되었는가?
- [ ] 에러 처리 및 복구 정책이 정의되었는가?
- [ ] 로깅·모니터링 요구사항이 명시되었는가?

## 3. Figma 디자인 명세 점검 항목

> Figma 링크가 제공된 경우에만 적용합니다.

### 3.1 화면 상태 완전성
- [ ] 빈 상태(Empty State)가 정의되었는가?
- [ ] 로딩 상태(Loading State)가 정의되었는가?
- [ ] 에러 상태(Error State)가 정의되었는가?
- [ ] 성공/완료 상태가 정의되었는가?

### 3.2 흐름 일치성
- [ ] 화면 전환 흐름(Navigation Flow)이 명세와 일치하는가?
- [ ] 모달·다이얼로그·바텀시트 등 오버레이 동작이 정의되었는가?
- [ ] 뒤로가기·취소 동작의 결과가 정의되었는가?

### 3.3 컴포넌트 및 시스템
- [ ] 기존 디자인 시스템 컴포넌트를 재사용하는가, 신규인가?
- [ ] 반응형 / 디바이스 대응(mobile, tablet, desktop) 여부가 명시되었는가?
- [ ] 접근성(Accessibility) 요구사항이 반영되었는가?

## 4. 사용자 확인 질문 템플릿

모호하거나 정의되지 않은 항목 발견 시 아래 형식으로 질문합니다.

```markdown
## ❓ 확인이 필요한 항목

1. [질문 1]: ~한 경우 어떻게 처리해야 하나요?
2. [질문 2]: ~의 기준값이 정해져 있나요?
3. [질문 3]: ~기능은 이번 범위에 포함되나요?
```

> ⚠️ 답변을 받기 전까지 해당 항목을 임의로 확정하지 마세요.

## 5. 자기 검증 체크리스트

Tech Spec 문서 작성 완료 후 반드시 아래 항목을 점검합니다.

### 5.1 내용 완전성

```markdown
## ✅ 자기 검증 — 내용 완전성

- [ ] 모든 기능의 입력 / 출력 / 예외가 정의되었는가?
- [ ] 작업 범위(Scope)가 명확하게 경계 지어졌는가?
- [ ] 사용자에게 확인받은 모든 항목이 문서에 반영되었는가?
- [ ] 새로운 기능이 사용자 동의 없이 추가되지 않았는가?
- [ ] 문서 내 상충되거나 중복된 내용이 없는가?
- [ ] 다른 에이전트가 이 문서만으로 작업을 시작할 수 있는가?
- [ ] 비기능 요구사항(성능, 보안, 로깅)이 누락되지 않았는가?
```

### 5.2 본문 작성 원칙 준수 (`tech-spec-template` 의 5원칙)

```markdown
## ✅ 자기 검증 — 작성 원칙

- [ ] **단정형**: 본문이 모두 "~ 한다 / ~ 이다" 단정형인가? "v?.? 정정", "이전엔 ~~ 였으나" 같은 회고 문장 없음?
- [ ] **버전 어노테이션 0건**: 본문(Section 0~8, 10~) 어디에도 `(vX.X 신설)` `(vX.X 정정)` `(vX.X 확정)` `(vX.X 해소)` 마킹이 없는가? 모든 변경 이력은 Section 9 Changelog 1줄로만 존재하는가?
- [ ] **Section 0 정의 단일 소스**: 도메인 용어 / 정책 수치 / invariant 가 Section 0 에만 정의되었는가? 본문에서 동일 용어 / 수치를 재정의하지 않고 참조만 하는가?
- [ ] **코드 위임**: 직접 코드 구현 본체(`var body: some View { ... }`, Reducer body, 알고리즘 본체)가 본문에 없는가? 코드는 타입 시그니처 + "참조 패턴: 파일경로:심볼" 형태로만 표기되었는가?
- [ ] **결정 과정 분리**: trade-off 비교표·대안 검토가 본문에 잔존하지 않는가? 결정 결과만 단정형으로 기재되었는가?
```

### 5.3 수명 관리

```markdown
## ✅ 자기 검증 — 수명 관리

- [ ] **해소된 미결 제거**: Section 8 에서 ✅ 해소 표시로 누적 보존된 항목이 없는가? 해소된 결정은 해당 절(예: 0.2 정책 / 3.x / 5.x)에 단정형으로 흡수되었는가?
- [ ] **Changelog 80자 1줄 포맷**: Section 9 의 모든 행이 80자 이내 1줄 요약인가? 산문 단락이 없는가?
- [ ] **자기 검증 비누적**: 이전 버전의 자기 검증 결과가 본문에 잔존하지 않는가? (별도 `self_check_log.md` 분리 또는 최신 1회만 유지)
- [ ] **별도 "주의 사항" 섹션 부재**: 회고 / 정정 / 권고 누적용 별도 섹션이 만들어지지 않았는가? 반복 누락 패턴은 Section 0 정의 또는 invariant 로 흡수되었는가?
- [ ] **본문 분량**: 본문이 1000라인을 초과하지 않는가? 초과 시 API 매핑 / Figma 채록 / LangSet 상세 / ADR 등 분리 대상 식별?
```

> 누락 또는 오류 발견 시 직접 수정합니다. 반복적으로 누락되는 패턴이 발견되면 **Section 0 정의 또는 invariant 로 흡수**합니다 — 별도의 "주의 사항" 섹션을 만들어 회고를 누적시키지 않습니다.
