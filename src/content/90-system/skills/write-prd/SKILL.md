# PRD 작성 절차

PRD는 **"왜, 누구를 위해, 무엇을, 어디까지"** 를 정하는 문서다. "어떻게"는 Tech Spec(`tech-spec-template`)의 몫이며 여기 적지 않는다.
산출 경로: `docs/{피쳐명}/prd.md`. 인수 조건은 `acceptance-criteria` 스킬로 `docs/{피쳐명}/acceptance.md`에 따로 만들고 PRD에서 링크한다.

## 0. 입력 확인
- 문제 설명, 대상 사용자, 참고 자료(Figma, 티켓, 데이터, 경쟁 사례)를 모은다.
- **문제가 한 문장으로 안 써지면 PRD를 쓰지 않고 사용자에게 묻는다.** 해결책부터 적힌 요청은 "어떤 문제를 푸는가"로 되돌린다.

## 1. 작성 원칙
- **단정형.** "~할 수도 있다", "가능하면" 금지. 결정된 것만 쓰고, 미결은 8절 열린 질문으로 보낸다.
- **측정 가능한 목표.** 목표마다 지표와 기준선, 목표치, 측정 시점을 붙인다. 못 붙이면 목표가 아니라 바람이다.
- **비목표를 목표만큼 진지하게.** 이번에 하지 않는 것을 적어야 범위가 지켜진다.
- **범위 보존.** 기능을 임의로 추가하지 않는다. 추가가 필요하면 사용자 확인 후 반영한다.
- **기술 결정 금지.** 아키텍처, 라이브러리, 데이터 모델은 적지 않는다. 필요하면 "Tech Spec에서 결정"으로 표시한다.
- **문서 크기 상한 2~3쪽.** 넘으면 피쳐를 나눈다.

## 2. 템플릿

```markdown
# PRD: {피쳐명}

| 항목 | 값 |
|---|---|
| 상태 | draft / review / approved |
| 작성자 | |
| 최종 수정 | YYYY-MM-DD (`date +%F`) |
| 관련 문서 | [인수 조건](./acceptance.md) · [Tech Spec](./spec_review.md) · [결정 기록](./decisions.md) |

## 1. 문제 (Problem)
- 누가, 어떤 상황에서, 무엇 때문에 불편한가. 한 문단. 데이터나 사례가 있으면 붙인다.

## 2. 대상 사용자 (Users)
| 사용자 유형 | 상황 | 지금의 우회 방법 |
|---|---|---|

## 3. 목표 (Goals)
| # | 목표 | 지표 | 기준선 | 목표치 | 측정 시점 |
|---|---|---|---|---|---|

## 4. 비목표 (Non-Goals)
- 이번에 하지 않는 것과 그 이유.

## 5. 범위 (Scope)
### 5.1 포함
- 사용자 관점의 기능 목록. 각 항목은 인수 조건 ID(AC-xx)와 연결한다.
### 5.2 제외
- 다음 단계로 미룬 것.

## 6. 사용자 흐름 (User Flow)
- 핵심 흐름 1~3개를 단계로. 화면 명세는 Figma 링크로 대체한다.

## 7. 리스크와 의존성 (Risks & Dependencies)
| 리스크 / 의존성 | 영향 | 대응 |
|---|---|---|

## 8. 열린 질문 (Open Questions)
| # | 질문 | 담당 | 기한 |
|---|---|---|---|

## 9. 변경 이력 (Changelog)
| 날짜 | 변경 | 이유 |
|---|---|---|
```

## 3. 자기 검증 (저장 전 필수)
- [ ] 1절 문제가 한 문단이고 해결책 언어가 없다
- [ ] 모든 목표에 지표·기준선·목표치가 있다
- [ ] 비목표가 1개 이상 있다
- [ ] 5.1의 각 기능이 인수 조건 ID와 연결된다 (없으면 `acceptance-criteria` 스킬 실행)
- [ ] 기술 결정이 한 줄도 없다
- [ ] 최종 수정일이 `date +%F` 결과다

## 4. 다음 단계
PRD가 `review` 이상이면 `acceptance-criteria` → `spec-reviewer`(Tech Spec) → `spec-to-ticket` 순으로 이어간다.
