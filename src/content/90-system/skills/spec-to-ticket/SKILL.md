# 스펙 → Jira 티켓 변환 워크플로우

검토 완료된 스펙 문서(`docs/{피쳐명}/spec_review.md`)와 Figma 디자인을 분석하여,
작업 단위로 분해하고 Jira 티켓을 생성하는 전체 프로세스입니다.

## 전체 흐름

```
1. 입력 수집        → 피쳐명 + prefix + Figma URL (또는 spec_review.md 경로)
2. 스펙 분석        → spec_review.md 읽기 + Figma 구조 파악 (보조)
3. 작업 분할        → API / 비즈니스 로직 / UI 단위로 분해
4. 문서화          → ticket_breakdown.md 생성
5. 사용자 검토      → 섹션별 순차 검토 + 수정
6. Jira 티켓 생성   → Jira MCP로 순차 생성 + 의존성 링크
```

---

## Step 1: 입력 수집

사용자에게 다음을 확인:

1. **피쳐명** (예: `login`, `payment`, `push-notification`)
2. **티켓 prefix** — 기본값은 `iOS`. 사용자가 다른 prefix를 제시하면 그것을 사용.
   - 예: `iOS` → `[iOS][API]`, `[iOS][UI]`, `[iOS]`
   - 예: `Android` → `[Android][API]`, `[Android][UI]`, `[Android]`
   - 예: `BE` → `[BE][API]`, `[BE]`
3. **Figma URL** — 있으면 받기, 없으면 spec_review.md만으로 진행
4. **상위 Jira 티켓** — 있으면 하위 작업으로 생성, 없으면 Jira 프로젝트 키 확인
5. **Jira 프로젝트 키** — 상위 티켓이 없을 경우에만 확인

이미 대화에서 제공된 정보는 다시 묻지 말 것.

---

## Step 2: 스펙 분석

### 2-1. spec_review.md 읽기 (우선순위 1)

```
docs/{피쳐명}/spec_review.md
```

파일이 있으면 **반드시 먼저 읽기**. spec_review.md가 분석의 주 입력값이다.

추출할 내용:
- **Section 0 정의** (`tech-spec-template` v4 이상에 신설)
  - 0.1 도메인 용어 — 티켓 제목 / 설명에 사용할 용어 통일
  - 0.2 정책 수치 — 각 티켓 상세에 인용할 수치 (예: "10문단 시 자동 진입", "trim 후 3~50자")
  - 0.3 invariant — 각 티켓의 PR 체크 항목으로 인용 (예: "Feature 간 직접 import 금지", "FontScale 영속화 금지")
- 기획 목적 및 배경
- 화면 목록 및 각 화면의 정책 / 로직
- API 요구사항 (Section 6)
- 비즈니스 로직 규칙
- 예외 처리 사항
- **참조 패턴 위치** (각 절의 "참조 패턴: 파일경로:심볼" 표기) — 해당 티켓 description 의 "참조 화면 / 코드 패턴" 섹션에 그대로 옮긴다. spec 이 의도적으로 코드 본체를 위임하므로, 티켓이 "어디서부터 시작해야 하는지" 의 진입점.

### 2-2. Figma 분석 (보조 수단, URL이 있는 경우)

spec_review.md에서 충분한 정보가 확보되면 Figma는 생략 가능.
시각적 구조 확인이나 spec_review.md에 빠진 세부 사항이 필요할 때 활용.

Figma MCP 도구 활용 순서:

```
1. get_metadata → 전체 노드 트리 조회 (화면/프레임 목록, description 텍스트)
2. get_design_context → 특정 화면 상세 조회 (필요한 경우만)
3. get_screenshot → 복잡한 화면 시각적 확인 (필요한 경우만)
```

description 텍스트 식별 기준:
- 레이어 이름에 "description", "정책", "spec", "desc" 포함
- TEXT 타입 노드에서 정책성 텍스트 추출

Figma 내용이 spec_review.md와 충돌하면 사용자에게 확인.

## Step 3: 작업 분할

### 분할 기준

prefix는 Step 1에서 결정된 값을 사용 (기본: `iOS`):

| 구분 | 티켓 제목 형식 | 내용 |
|-----|-------------|------|
| API 작업 | `[{prefix}][API] 제목` | API 연동, DTO 모델링, Domain 모델링 |
| 비즈니스 로직 | `[{prefix}] 제목` | UseCase, 모듈 설계, 비즈니스 규칙 구현 |
| 화면 작업 | `[{prefix}][UI] 제목` | UI 구현, 상태관리, 화면 라우팅 |

### 티켓 크기 기준

**목표: 커밋 5~10개 수준**

| 난이도 | 커밋 수 | 예상 기간 | 예시 |
|--------|--------|----------|------|
| 소 | 1~3개 | 0.5~1일 | 조건문 확장, DTO 필드 추가 |
| 중 | 4~7개 | 1~3일 | 화면 1개 구현, API 연동 |
| 대 | 8~12개 | 3~5일 | 비즈니스 로직 신규 구현, 복수 모듈 변경 |

커밋 1~2개짜리 극소 티켓은 인접 작업과 묶을 것.
커밋 15개+ 초과 티켓은 반드시 분리.

### 분할 체크리스트

**화면 작업:**
- [ ] F0 페이지 레이아웃 티켓 먼저 생성 (라우팅 + 페이지 구조 + 섹션 영역)
- [ ] F1~ 컴포넌트 티켓은 F0 의존성으로 설정
- [ ] 복잡한 컴포넌트는 별도 티켓으로 분리

**API 작업:**
- [ ] 엔드포인트 단위로 분리
- [ ] 공통 유틸/레이어는 별도 티켓

**비즈니스 로직:**
- [ ] 레이어/모듈별 책임 분리
- [ ] UseCase 의존성 및 경계 설정

### 의존성 원칙

```
1. 서버 API 구현 or API 명세
    ↓
2. F0 페이지 레이아웃 (라우팅, 빈 페이지)
    ↓
3. F1~ 컴포넌트 + API 연동
```

병렬 가능 케이스:
- API Payload 모델 선언 후 → 클라이언트 모델링 병렬 가능
- 독립적인 화면/API/로직끼리 병렬 가능

## Step 5: 사용자 검토

문서 작성 후 티켓 생성 전, 반드시 섹션별 검토 진행.

**검토 순서:**
1. 기획 요약 — 목적, 핵심 흐름 정확성
2. 화면/API/로직 목록 — 누락 여부
3. 작업 분할 테이블 — 티켓 범위, 의존성
4. 티켓 상세 — 작업 내용, API 스펙

**각 섹션마다:**
- 요약 + 검토 포인트 제시
- 사용자 OK → 다음 섹션
- 수정 필요 → 즉시 반영 후 다음

**티켓 상세 검토 시**: 작업 레포가 명시되지 않으면 사용자에게 확인.

## Step 6: Jira 티켓 생성

사용자 승인 후 진행. 의존성 순서대로 순차 생성.

**Jira MCP 도구(`mcp__atlassian__jira_create_issue`)를 사용한다.**

### 티켓 생성 순서 원칙

```
1. 선행 티켓 생성 → Jira 번호 확보
2. 후행 티켓 생성 → 본문에 선행 티켓 번호 명시
3. 반복
```

### Jira MCP 파라미터

```
project:     {Jira 프로젝트 키}
issuetype:   "하위 작업"  (상위 티켓 있을 때)
             "Task"       (단독 티켓일 때)
summary:     "[{prefix}][API] 티켓 제목"  등 prefix에 맞게
description: 아래 형식 참조
parent:      {상위 티켓 번호}  (있을 경우만)
assignee:    @me
```

**주의**: labels 필드는 사용하지 않음.

### 티켓 description 형식

breakdown 문서의 "티켓 상세" 섹션을 읽어서 조합:

```
**피쳐명**: {피쳐명}

**설명**:
{설명 내용}

**작업 내용**:
- [ ] 항목 1
- [ ] 항목 2

**API 스펙** (API 작업 시):
{API 명세}

**참조 화면** (UI/로직 작업 시):
{피그마 화면명}

**의존성**:
- 선행: {선행 티켓 번호 또는 "없음"}
```

`**피쳐명**` 필드는 `create-task` 스킬이 태스크 파일 경로(`docs/{피쳐명}/`)를 자동으로 결정하는 데 사용됩니다. 반드시 모든 티켓에 포함시킵니다.

### 의존성 링크 설정

티켓 생성 후 `mcp__atlassian__jira_create_issue_link`로 선행-후행 관계 설정:
- 선행 티켓 번호와 후행 티켓 번호가 모두 확보된 시점에 링크 생성
- link type: "Blocks" 또는 프로젝트에서 사용하는 링크 타입 확인 후 적용

## 복수 기획 묶음 (폴더링)

사용자가 여러 기획을 하나의 큰 작업으로 묶으라고 할 때:

**트리거**: "이 작업들 묶어줘", "하나의 프로젝트로 관리", "폴더로 정리해줘"

**폴더 구조:**
```
docs/{작업명}/reviewed_spec_to_ticket/
├── _overview.md                   # 전체 개요, 관계도, 작업 순서
├── 01-{기획1}-breakdown.md
├── 02-{기획2}-breakdown.md
└── ...
```

## 주의사항

- **링크 1개 = 파일 1개**: Figma URL/스펙을 받을 때마다 별도 breakdown 파일 생성
- **과도한 분할 금지**: 커밋 1~2개짜리 극소 티켓은 인접 작업과 묶기
- **사용자 검토 필수**: 티켓 생성 전 반드시 분할 결과 검토받기
- **유연하게 조정**: 작업 중 티켓 분리/병합 허용
