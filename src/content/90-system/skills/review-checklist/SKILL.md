# 리뷰 체크리스트

플랫폼별 코드 규칙(Swift, Kotlin, TS)은 각 저장소의 규칙과 플랫폼 스킬이 다룬다. 이 체크리스트는 **플랫폼과 무관하게 항상 묻는 질문**이다.
결과는 아래 표로 PR 코멘트 또는 `docs/{피쳐명}/review.md`에 남긴다. 판정은 `통과 / 지적 / 해당 없음(이유)` 셋 중 하나다.

## 1. 완료 판정
| # | 질문 | 판정 |
|---|---|---|
| 1.1 | `docs/{피쳐명}/acceptance.md`의 AC 중 이 PR이 닫는 것이 명시되어 있는가 | |
| 1.2 | 닫힌 AC마다 검증 방법(테스트, 수동 확인)의 증거가 PR에 있는가 | |
| 1.3 | Tech Spec의 정책 수치·불변식(Section 0)을 위반한 코드가 없는가 | |
| 1.4 | 범위 밖 변경(리팩터링, 무관한 수정)이 섞여 있지 않은가 | |

## 2. 실무 설계 원칙 (세컨드 브레인 🧭에서 승격된 항목)
| # | 질문 | 판정 |
|---|---|---|
| 2.1 | **재시도가 있는 곳에 "이미 했는가"를 판별하는 진실 원천이 있고, 필요하면 둘 이상을 합치는가** (멱등성) | |
| 2.2 | **일시적 실패를 종결이 아니라 보존(pause, 재개 가능)으로 다루는가**, 특히 사용자 비용이 큰 작업에서 | |
| 2.3 | **단일 소비자 프리미티브(AsyncStream, Channel, Flow collect 등)를 둘 이상이 소비하지 않는가** | |
| 2.4 | **리소스 생성 직후 실패에 보상 동작이 짝지어져 있는가** (서버에만 남는 유령 리소스 방지) | |
| 2.5 | **공유 가변 상태의 소유자가 하나인가** (actor, 단일 reducer, 단일 store). 락과 큐가 뒤섞이지 않았나 | |
| 2.6 | **의존 방향이 지켜지는가** (Feature→Core만, Feature 간 직접 참조 없음, 외부 SDK는 래퍼 뒤) | |
| 2.7 | **"정확히 한 번" 계약이 있는 콜백에 가드가 있는가** (완료 핸들러, 백그라운드 깨어남) | |

## 3. 안전성
| # | 질문 | 판정 |
|---|---|---|
| 3.1 | 비밀값, 토큰, 내부 URL이 코드나 로그에 없는가 | |
| 3.2 | 사용자 데이터 삭제·덮어쓰기 경로에 확인이나 되돌림이 있는가 | |
| 3.3 | 에러가 조용히 삼켜지는 곳(빈 catch, 무시된 Result)이 없는가 | |

## 4. 테스트와 문서
| # | 질문 | 판정 |
|---|---|---|
| 4.1 | 예외 흐름 AC에 해당하는 테스트가 있는가 (정상 흐름만 테스트하지 않았나) | |
| 4.2 | 대안을 비교해 택한 결정이 있으면 `decisions.md`에 기록됐는가 (`record-decision`) | |
| 4.3 | 명세 결함을 발견했으면 spec `update`로 반영했는가 (구현 결과를 spec에 sync하지 않았는가) | |
| 4.4 | 커밋 메시지가 `commit-message` 규칙(제목 한 줄, Conventional Commits, 서명 없음)을 따르는가 | |

## 5. 결과 요약 형식
```markdown
### 리뷰 결과: {통과 | 수정 필요}
| 구분 | 통과 | 지적 | 해당 없음 |
|---|---|---|---|
| 완료 판정 | | | |
| 설계 원칙 | | | |
| 안전성 | | | |
| 테스트·문서 | | | |

**지적 사항 (수정 필요)**
1. {체크 번호} {파일:줄} {무엇이 왜 문제인지 한 문장} → {제안}

**잘한 점**
- 한두 줄.
```

## 6. 체크리스트 자체의 갱신
2절은 세컨드 브레인 용어집의 🧭 섹션에서 승격된 원칙이다. 새 원칙이 용어집에 쌓이면 여기 한 줄을 추가하고, 이 파일의 변경은 공용 절차 패키지 저장소에 커밋한다. 저장소별 사본을 만들지 않는다.
