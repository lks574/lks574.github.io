# 인수 조건 작성 절차

인수 조건(Acceptance Criteria, AC)은 **"이 기능이 끝났다"를 사람과 에이전트가 같은 방식으로 판정하는 문장**이다.
산출 경로: `docs/{피쳐명}/acceptance.md`. PRD 5.1의 기능 항목, Tech Spec 3.x의 기능 명세, QA 시나리오가 모두 AC ID로 연결된다.

## 0. 입력
- `docs/{피쳐명}/prd.md`가 있으면 5.1 포함 범위를 기준으로 삼는다. 없으면 사용자 설명을 기준으로 삼고 PRD 부재를 명시한다.
- Figma가 있으면 화면 상태(빈 상태, 로딩, 에러, 성공)를 AC에 반영한다.

## 1. 작성 원칙
- **한 AC에 한 판정.** "그리고"로 이어진 조건은 둘로 나눈다.
- **관찰 가능한 결과만.** "빠르게", "적절히" 금지. 숫자나 상태로 쓴다.
- **정상 흐름보다 예외 흐름에 더 많은 AC.** 네트워크 실패, 권한 없음, 중복 요청, 중단 후 재진입, 빈 데이터는 기본 포함.
- **비기능도 AC다.** 성능, 접근성, 오프라인, 다국어는 측정 기준과 함께 적는다.
- **ID는 불변.** `AC-{피쳐약어}-{번호}`. 삭제하면 `폐기`로 표시하고 번호를 재사용하지 않는다.

## 2. 템플릿

```markdown
# 인수 조건: {피쳐명}

| 항목 | 값 |
|---|---|
| 기준 문서 | [PRD](./prd.md) · [Tech Spec](./spec_review.md) |
| 최종 수정 | YYYY-MM-DD |

## 요약
| ID | 기능 (PRD 5.1) | 유형 | 상태 |
|---|---|---|---|
| AC-XX-001 | | 정상 / 예외 / 비기능 | 제안 / 확정 / 폐기 |

## AC-XX-001 {한 줄 제목}
- **Given** 전제 상태
- **When** 사용자 또는 시스템의 행위
- **Then** 관찰 가능한 결과 (숫자, 상태, 화면, 저장된 데이터)
- 검증 방법: 수동 / 단위 테스트 / UI 테스트 / 로그 확인
- 관련: PRD 5.1-n · Spec 3.n · Figma 프레임

## 예외 흐름 체크 (각 기능마다 답한다)
| 상황 | AC ID 또는 "해당 없음(이유)" |
|---|---|
| 네트워크 실패 / 타임아웃 | |
| 권한 없음 / 로그아웃 상태 | |
| 중복 요청 (연타, 재시도) | |
| 중단 후 재진입 (앱 종료, 백그라운드) | |
| 빈 데이터 / 최대치 | |
| 다국어 / 긴 문자열 | |
```

## 3. 자기 검증
- [ ] PRD 5.1의 모든 기능에 AC가 1개 이상 있다
- [ ] 예외 흐름 표의 모든 행이 채워져 있다 ("해당 없음"에는 이유가 있다)
- [ ] Then에 형용사만 있는 문장이 없다
- [ ] 모든 AC에 검증 방법이 있다

## 4. 다음 단계
- Tech Spec 작성 시 `spec-reviewer`가 3.x 기능 명세의 예외 흐름 표를 이 문서의 AC ID로 연결한다.
- QA 에이전트는 이 문서의 AC를 시나리오 테스트의 정답지로 쓴다. `qa_result.md`는 AC ID별 통과/실패를 기록한다.
