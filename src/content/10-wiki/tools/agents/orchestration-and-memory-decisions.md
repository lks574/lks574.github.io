## 1. 맥락과 제약 (Context)

- 2026년 8월부터 Orca 오케스트레이션 Run 12개를 돌렸다. 대상은 iOS 앱, Android 앱, React Native 브라운필드 이관, 개인 사이트, 세컨드 브레인이다.
- 쓰는 에이전트는 Claude Code, Codex, Antigravity 세 종류다. 각각 메모리, 규칙 파일 위치, 스킬 폴더가 다르고 서로의 대화를 모른다.
- 혼자 일하므로 리뷰어가 따로 없다. 판단이 필요한 설계 질문에서 한 에이전트의 답을 그대로 믿으면 검증이 없는 셈이다.
- 개인 위키는 노트 수십 개 규모다. 벡터 DB를 붙일 만큼 크지 않고, 붙이면 유지 비용이 콘텐츠 비용을 넘는다.

## 2. 선택한 구조 (Decision)

1. **판단이 갈리는 질문은 두 에이전트에 같은 브리프를 주고 독립 실행한다.** 상태 관리 방식 선택, 정보 구조 재설계, 진행 방식 채점처럼 정답이 없는 문제에서 Codex와 Claude, 또는 Claude와 Antigravity의 답을 나란히 놓고 겹치는 지적을 신뢰한다. 12개 Run 중 5개가 이 형태였다.
2. **역할은 메인 하나와 서브 하나로 고정한다.** Claude가 방향 합의, 작업 분해, 편집, 종합, 커밋을 맡고, Antigravity는 독립 검증과 리뷰, 대량 읽기처럼 위임된 작업만 한다. 구현자와 리뷰어를 분리하는 것이 목적이다.
3. **컨텍스트는 파일 브리프로 넘긴다.** 워커는 코디네이터의 대화와 메모리를 모르므로, 목표·읽을 파일·허용 명령·산출 경로·완료 조건을 한 파일에 자기완결적으로 쓰고 그 경로만 넘긴다. 결과도 파일로 받는다.
4. **매번 읽히는 것과 막힐 때 읽는 것을 나눈다.** 규칙 파일(AGENTS.md)과 스킬은 매 세션 로드되므로 짧게 유지하고, 위키와 용어집은 링크와 `llms.txt`로 찾아가는 참조층으로 둔다. 용어집을 모든 컨텍스트에 주입하지 않는다.
5. **개인 위키에는 검색 증강 시스템을 붙이지 않는다.** 원자 노트, 양방향 링크, 빌드 타임 자동 색인, `glossary.json`과 `llms.txt`만으로 에이전트가 grep과 파일 읽기로 찾아간다. 임베딩과 벡터 DB는 노트가 수백 개를 넘고 grep이 실패하기 시작할 때 다시 본다.
6. **방향 합의는 에이전트 메모리가 아니라 저장소 문서(헌장)에 남긴다.** 메모리는 헌장을 가리키는 포인터와 세션 연속성 사실만 갖고, 방향 내용을 복사하지 않는다. 둘이 다르면 어느 쪽도 자동으로 이기지 않고 멈춰서 사람과 정한 뒤 하나만 고친다.
7. **기억은 세 층으로 승격한다.** PR과 트러블슈팅(일화) → 설계 기록과 용어집 🧭(의미) → 리뷰 체크리스트와 규칙(절차). 승격이 됐는지는 사람 기억에 맡기지 않고 린트가 매 실행 보고한다.

## 3. 버린 대안과 이유 (Alternatives)

- **에이전트 하나에 다 맡기기:** 빠르지만 검증이 없다. 실제로 구현자가 쓴 결정 기록의 전제가 코드와 달랐던 것, 항상 통과하는 테스트, 조용한 미탐 버그를 독립 리뷰어가 6건 잡았다. 작성자는 자기 전제를 의심하지 않는다.
- **채팅으로 컨텍스트 전달:** 워커 터미널에 긴 프롬프트를 흘려 넣으면 잘리고, 재시도할 때 같은 내용을 다시 만들 수 없다. 파일은 재현되고 diff가 남는다.
- **위키 전체를 시스템 프롬프트에 주입:** 토큰만 쓰고 대부분은 그 작업과 무관하다. 필요한 노트만 링크로 찾아 읽는 쪽이 싸고 정확했다.
- **벡터 DB 기반 RAG:** 수십 개 노트에 임베딩 파이프라인, 인덱스 갱신, 청킹 규칙을 유지하는 비용이 얻는 것보다 크다. 파일명과 링크가 이미 좋은 인덱스다.
- **메모리를 정본으로 쓰기:** 에이전트별로 따로 있고, 사람이 보지 않고, 버전 관리가 없다. 다른 도구는 존재도 모른다. 정본이 될 자격이 없다.
- **검증 전 전역 적용:** 공용 스킬을 홈 폴더 전체에 설치했다가 되돌렸다. 한 저장소에서 검증한 뒤 지시로 넓히는 것이 맞았다.

## 4. 결과 (Outcome)

- 진행 방식 채점: Claude 30/50, Antigravity 33/50, 공통 지적 일치. 하루 뒤 독립 리뷰가 지적 6건을 냈고 전부 사실이었다.
- 두 도구가 같은 규칙 파일(AGENTS.md)과 같은 스킬 원본을 읽는다. 스킬 폴더는 링크 두 곳.
- 승격 대기 건수와 🧭 보유 비율이 린트 마지막 두 줄에 매번 표시된다.

## 5. 🧭 얻은 원칙 & 관련 용어 (Lesson)

- **정답이 없는 질문은 에이전트 둘에게 독립으로 묻고 겹치는 답을 믿는다. 구현자와 리뷰어는 다른 에이전트여야 한다.** → [[agent-orchestration]]
- **워커에게 넘기는 컨텍스트는 자기완결적인 파일 하나다. 매번 읽히는 것은 짧게, 참조는 링크로.** → [[context-window]]
- **개인 규모의 지식은 검색 시스템보다 좋은 파일명과 링크가 먼저다. RAG는 grep이 실패할 때 붙인다.** → [[rag]]
- **기억은 저장소가 정본이고 메모리는 포인터다. 승격이 됐는지는 도구가 보고한다.** → [[memory-consolidation]]
- **측정할 것을 먼저 정한다.** 에이전트로 구현 리드타임이 줄었다는 것도 전후를 재서 알았고, 그 뒤로 기획 문서의 목표에는 지표·기준선·목표치를 필수로 붙인다. → [[lead-time]]
